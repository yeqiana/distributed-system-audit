## 实际链路与状态

本轮相关路径仅为 scenarios.py 的 delivery()，没有证据将同文件 lease、outbox、read_health 等独立示例接入该链路。

```text
delivery()
  -> 内存 SQLite receipt(receiver 主键, status)
  -> 初始化 receiver 0..99 = PENDING
  -> 单线程遍历
       receiver 0..98：UPDATE 为 SENT
       receiver 99：ConnectionError -> catch -> continue
  -> parent_status = DONE（普通局部变量，无聚合条件）
  -> retry_tasks = []
  -> 汇总 receipt 状态并返回
```

| 边界 | 写入/读取及责任 | 标识、重试、完成标准 |
| --- | --- | --- |
| 批次入口 | delivery() 初始化并处理；真实调用方未提供 | 模型没有 batch_id、请求幂等键或版本 |
| 单项记录 | delivery() 写 receipt；最终 GROUP BY 只统计 | receiver 主键；只代表模型单项身份，无法证明跨批次去重 |
| 发送 | 源码以异常分支和 SENT 更新代替真实下游 | 无真实下游调用、ACK、超时语义或幂等保证证据 |
| 异常处理 | catch ConnectionError 后继续 | 无次数、退避、错误记录或重试执行者 |
| 父完成 | 循环结束写局部 parent_status | 当前条件为“循环退出”；契约要求“全部送达” |
| 恢复/健康 | retry_tasks 恒为空；契约明确无扫描器、外部队列 | 无自动修复 owner、告警入口或 RTO |

receipt 中未成功项保留 PENDING，可用于定位候选失败对象；这只保留了线索，不等于存在可执行的恢复闭环。内存 SQLite 没有模拟持久化存储，不能据此确认真实系统的 commit、进程重启恢复或持久性。

状态推导：PENDING -> SENT；异常时 PENDING -> PENDING。父批次初始状态未建模，循环结束后直接 -> DONE。当存在 PENDING 时进入 DONE，在本案例明确契约下属于非法完成。未规定必须使用哪一个替代状态名称。

## 核心不变量

1. parent=DONE 当且仅当本批次所有目标接收者均已确认成功送达；已知仍存在 PENDING 时不得宣称成功完成。
2. 失败或未确认的合法接收者必须保留处理意图，并存在明确执行者、重试或人工恢复入口，直至成功或明确对外表达的失败终态。
3. 部分成功恢复应按接收者粒度选择尚未完成项；不得因为父完成标志而跳过失败项，也不得为了补一人直接无条件重发全部成功项。
4. 健康/验收应与同一业务完成契约一致：仅看到 DONE 不能掩盖单项未完成。

其中 1 为显式契约；2-4 为本次“批次处理与恢复”范围下由该完成契约推导的必要恢复/验收要求。实际下游 exactly-once 或至少一次承诺未知，不自行假定。

## 已确认问题与二次复核

### F1：部分失败被错误完成，失败对象没有恢复执行者

- 状态：合成模型内已确认；生产影响未验证。
- Impact：对模型业务契约影响高。一个接收者未收到消息，父批次却报告成功；依赖父状态的调用方可能停止追踪或重试，漏发无法自动收敛。
- Likelihood：给定模型 receiver=99 的异常前提，控制流必然产生错误终态；真实下游异常概率、用户规模、业务紧急程度未知。
- 建议优先级：优先修复（临时建议，不套用未提供的项目 P0/P1 标准）。应先阻止假成功并闭合单项恢复，再扩大自动重试。
- 违反不变量：1、2，并给 3、4 带来恢复与观测要求。
- 可达路径：初始化 100 个 PENDING（30-31）-> 99 个更新 SENT（32-36）-> 最后一个异常被 catch 后 continue（34-38）-> 不检查单项结果便设置 DONE（39）-> 没有重试任务（40）。不存在提前 return、异常传播或完成前聚合校验阻断该路径。
- 根因：把“遍历结束”当作“业务全部送达”，且单项异常未进入有责任人的恢复流程。错误完成与空恢复不是两个相互独立的漏发事故，合并为一个治理包，但修复两方面才可关闭。
- 观察证据：observed.json:2-7 与该源码路径一致，显示 DONE / 99 SENT / 1 PENDING / 无重试。
- 测试证据：本轮未运行。源码和输入观察支持本案例结论；不称为本轮确定性复现。
- 反证检查：catch 后继续可以有意让其他接收者不被单个失败阻断，这一设计本身不是缺陷；但不足以满足 DONE 契约。PENDING 线索尚在，也不能替代扫描器/队列/人工恢复入口；contract.md 明确排除了自动扫描和外部队列。若实际系统另有恢复机制，需要提供并验证，不以想象的机制否定当前模型证据。
- 需要处理：代码语义修复、永久回归、恢复操作与监控契约；当前只读任务不实施。

| 项目 | 二次评审结果 | 处理方式 |

| 部分失败仍 DONE | 明确契约违例，材料与控制流相互印证 | 必须修复完成判定 |

## 排除项与范围控制

- 不把单个异常后继续处理其他人报为缺陷，问题是最终成功语义和恢复责任。
- 不把 PENDING 残留直接称为不可恢复数据丢失：线索尚在，但没有已知自动执行路径；人工是否有现成入口未知。
- 不宣称真实数据库发生部分提交、真实 broker ACK 后丢失、真实发送重复或并发覆盖；模型没有相关组件和时序证据。
- 不因 lease_free 中 PROCESSING + null lease 报缺陷。该独立示例有状态条件更新和 effect 主键；与 delivery 无调用关系，本轮不扩展审计。
- 其他 lease、outbox、read_health 函数为同文件独立模型，未纳入消息批次实际链路，不凑成额外发现。

## 恢复闭环

| 要素 | 当前证据 | 修复与验收要求 |
| --- | --- | --- |
| Failure | 单项下游 ConnectionError，父却 DONE | 明确表达部分成功/未完成，保留失败对象与原因 |
| Detection | 可查询 receipt PENDING 并与父聚合对照；无执行检测者证据 | 由指定组件检查 DONE 与 receipt 不一致及 pending 超龄；告警阈值由业务确认 |
| Durable intent | 模型有 PENDING 记录；真实持久性未验证，无外部恢复队列 | 在实际已有处理记录/任务机制中可靠保留，验证提交与崩溃窗口，无需预设引入新框架 |
| Repair owner | 当前无自动扫描器、无外部恢复队列；人工入口未知 | 指定单项重试执行者与人工接手入口，确认不会被父 DONE 过滤 |
| Retry | 无次数、退避、上限或错误分类证据 | 按实际下游区分可重试与永久错误，设退避/上限，超限可观察并可人工恢复 |
| Convergence | 当前 receiver 99 保持 PENDING，无自动推进机制 | 恢复后全部确认送达再 DONE；永久失败不能伪装 DONE |
| RTO | 未提供 | 业务指定目标时长后，以故障解除到最后单项/父状态收敛的实测验证 |
| Residual cleanup | 未提供残留清理流程 | 对历史 DONE+PENDING 建清单，逐项确认真实下游送达事实，幂等补发并核对最终状态 |

历史数据恢复方案仅为建议，不已执行：只按 parent=DONE 筛选会错过失败项，须同时核对 receipt。重新发送前需要实际下游去重/送达查询证据；不能直接把所有 PENDING 改成 SENT，不能把 DONE 契约改成“遍历完成”来消除报警，也不能无条件重发整个批次。

## 治理包、顺序、上线与回滚

G1：批次完成语义与单项恢复。关联 F1；涉及批次处理、单项状态、父完成判定、恢复执行者与状态消费者。最小目标是完成判定依赖真实单项成功，并使失败项有实际可达的恢复责任人。优先沿现有 receipt/parent 设计收口，不要求新框架、接口、数据库结构或队列；任何确需公共接口或结构变更须另行评审。

顺序：先核对调用方对 DONE 的依赖与单项状态持久性；再修复成功聚合并闭合失败项恢复；随后补永久回归和检测；最后核对并修复历史不一致。不能只改 parent 状态后让 PENDING 永久悬挂。

上线 Gate：100/100 与 99/1 场景语义正确；失败项可独立重试成功；重启、重复触发、确认丢失场景可收敛；关键调用方识别未完成状态；RTO 与告警责任明确；历史不一致清单和补发方案可审核。上述均未执行。

兼容与回滚：确认新旧 worker/调用方的状态识别、重试去重及记录读取兼容。若旧 worker 会无条件 DONE，需发布与回滚时防止该路径重新接管；保留待恢复记录和运行证据，避免回滚清空恢复意图。具体停用/切换操作需在实际部署验证并另获具体授权，本次不操作服务。

关闭条件：不仅是代码更改或旧测试通过，必须有永久业务回归、故障/恢复实证、调用方兼容、可观察告警、历史残留处理及适用的回滚验证。当前 F1 未修复、未关闭。
