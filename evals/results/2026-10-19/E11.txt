## 理解、计划与风险

理解：判断现场状态是否违反本例契约，以及完成处理能否重复、能否发生半提交。计划：核对状态契约，跟踪目标函数，检查重复与事务边界，复核反证和恢复缺口。风险：只有最小合成模型，缺少实际调用方、持久化生产库和执行调度；源代码推断与给定记录不能替代真实运行验收。

## 实际链路与不变量

链路：初始化 job(id=1, PROCESSING, lease=NULL) 并提交 → 执行一次事务 → UPDATE job WHERE id=1 AND status=PROCESSING → 更新命中才 INSERT effect(job_id=1) → 提交 → 再次调用时 UPDATE 命中 0 行、不插入 effect。

job.id 是状态对象标识，effect.job_id 主键是副作用唯一标识。完成资格由数据库条件更新决定，不存在 lease 领取、续租、抢占或 generation 协议。此模型没有外部 HTTP/MQ/cache/outbox 或独立读服务。完成判据为业务 effect 与 COMPLETED 一起持久化，而非仅函数返回。

必须保持：

1. 允许 PROCESSING 且 lease=NULL；不能凭空添加租约状态限制。
2. 同一 job 最多一个 effect；重复完成不能新增 effect。
3. 正常提交路径中 COMPLETED 与 effect 一起出现；effect 插入失败不得保留提前写入的 COMPLETED。
4. COMPLETED 后重复调用不再次处理、不逆转终态。

## 已确认行为、反证与可达路径

| 场景 | 材料支持的行为 | 证据性质及结论 |
| --- | --- | --- |
| 初始 PROCESSING、无 lease | 初始化合法，执行器无需领取租约 | 契约明示 + 源码；排除“无租约必然失控”误报 |
| 第一次完成 | 条件更新 1 行，插入 1 个 effect | 给定 observed 与源码相符；本次未运行复现 |
| 同一 job 顺序重复完成 | 更新 0 行，不再插入；effect 总数 1 | 给定 observed；排除本模型顺序重复副作用 |
| UPDATE 后 INSERT 报错 | with db 事务应回滚 UPDATE，不能单独提交 COMPLETED | 契约保证、源码推断；故障未注入，仍需验证 |
| 两执行者并发完成 | 条件 UPDATE 与主键提供防重基础；SQLite 写竞争可能有等待或锁错误 | 未做多连接并发；不能将顺序两次调用当作并发证据，锁错误恢复策略未知 |
| 提交前后进程退出 | 原子事务提供恢复基础；提交前回滚、提交后重试应命中 0 行 | 未实际 crash；当前 :memory: 库无法验证持久化重启恢复 |

已确认缺陷：无。无目标项目严重性标尺，不赋予通用 P0/P1，也不为排除项制造修复级别。当前应优先补证据，而非引入租约或改公共状态机。

现有反证足以排除“必须使用 lease”“没有 outbox 就丢外部消息”“旧 owner 必然覆盖新 owner”等判断：这些并非本例机制或副作用范围。不能把根本不存在的跨系统调用链硬套到此模型。

## 恢复闭环与未验证项

- effect 插入失败：事务回滚提供一致性保障；后续由谁发现仍为 PROCESSING、谁重新调度、退避和重试上限未提供。失败发生时是否自动重试未知，不认定任务必然永久卡死。
- 事务提交前崩溃：给定原子性契约应防止半提交，但实际持久化库的恢复与再次执行未测。
- 事务提交后响应丢失：重复调用按条件更新应无新增副作用；响应协议、重试调用方和状态读取路径未提供。
- 并发锁冲突：没有并发执行记录，异常是否被上层捕获和重试未知。
- 检测与运维：没有告警、积压扫描、人工重放入口、恢复责任人和 RTO 材料；属于证据缺口，不是已确认缺陷。
- 数据范围：没有异常历史数据写入或其他 writer 的证据；无法证明任意 writer 都遵守相同事务，也不能虚构不一致历史记录。observed 未输出最终 status，需补直接查询验证终态。

## 最小回归与验收计划（未执行）

只读要求下不运行任何写数据或故障注入探针。下列均为后续隔离环境测试设计，不是本次通过结果：

1. 正常及顺序重试：查询 job.status、effect 数量、影响行数；应分别为 COMPLETED/1/[1,0]。
2. UPDATE 成功后令 INSERT effect 失败：应抛错并回滚，状态仍 PROCESSING、effect=0；取消故障后重试可完成，最后 effect=1。
3. 两独立连接竞争同一 job：同步起跑，断言最多一次成功、effect=1；若出现锁错误，验证上层重试最终收敛。不能只检查最终计数而忽略永久未完成。
4. 隔离持久化数据库的进程故障：提交前退出，重启后无半提交且可重试；提交后响应前退出，重启重试无重复 effect。内存库不能承担此项验收。
5. 验证真实调用方和调度器：失败后的任务可被再次发现，明确责任人、重试策略、人工入口和 RTO；保留真实结果与告警证据。

没有代码修复治理包。按“正常/回滚证据 → 并发 → 持久化崩溃恢复 → 调度与 RTO”补齐验收即可；只有出现真实违约再按根因修复。未授权实施或发布，无需设计本次代码回滚；后续如改动，需另验事务、幂等契约、旧调用方兼容及回滚版本行为。

## 大白话解释

这里 PROCESSING 表示“事情还没办完”，不表示“某人已经拿到租约”。数据库负责把“改成完成”和“写入业务结果”一起落地；第二次处理因任务已完成而不会再写结果。材料已经说明这种设计允许租约为空，真正还需补测的是多人同时处理和进程突然退出后的恢复。
