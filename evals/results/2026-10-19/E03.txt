# E03 只读分布式审计报告

## 结论与执行边界

确认 1 项合成模型内的真实合同违约：`lease(False)` 中，A 在 B 接管并完成后恢复，仍能覆盖 B 的任务结果。材料自带 SQLite 轨迹显示旧 A 更新影响 1 行，最终 owner=B、generation=2、status=COMPLETED，result 却为 A-result。任务结果用于业务读取，因此不是仅有代码风格或日志问题。

真实性边界：全部材料是合成评测输入；这不是生产事故证明。本轮未运行 scenarios.py，未执行 SQL、故障注入、网络访问或服务操作。只读要求及 skill 的执行边界禁止本轮注入故障，因此使用材料自带执行轨迹及完整源码链作证据，补充只读 JSON 核对。workspace 为空，无法确认实际部署版本、真实服务调用方、数据库实现或事故频率。除本报告外无文件修改。

## 实际链路与状态

1. 创建内存 SQLite job(id PRIMARY KEY, owner, generation, status, result)。任务主键是 id=1。
2. A 的初始状态为 owner=A、generation=1、PROCESSING、result=NULL（scenarios.py:11–13）。模型以初始化表示 claim，没有真实调度/租约时间实现。
3. B 接管：同一 id 的 owner 改 B、generation 改 2（:14）。该接管被合同定义为有效前提，不另猜租期计算。
4. B 以 id、owner=B、generation=2 为条件完成，得到 COMPLETED/B-result（:15）。
5. A 恢复，持有旧身份 A/1。guarded=false 时生成的 SQL 只有 WHERE id=?（:17–22），既不检查 owner/generation，也不检查 PROCESSING。
6. SQLite 接受更新，A 把 status 再写成 COMPLETED，把 result 写为 A-result；owner/generation 保持 B/2。业务 reader 使用此结果将读到过期 worker 输出（合同规定，未给 reader 代码）。

没有材料证明存在 MQ、Outbox、缓存、外部副作用、定时扫描、告警或修复入口；不能为该链路凭空添加这些组件。此模型只有内存数据库，关闭即销毁，不能宣称具备跨进程持久恢复能力。

## 核心不变量与非法转移

- I1【合同明确】：接管到 B/2 后，A/1 的完成更新必须被拒绝，影响行数应为 0，且不能改变 B 的结果。
- I2【由业务读取合同推导】：结果及其 owner/generation 必须属于同一次授权完成；不能让 B/2 元数据包装 A/1 的旧结果。
- I3【由 I1/I2 推导】：COMPLETED 必须意味着当前授权执行者的有效完成结果。状态文字不变并不能掩盖结果被改写。
- 合法路径：A/1 PROCESSING → B/2 PROCESSING → B/2 COMPLETED/B-result；随后 A/1 完成应成为拒绝或无效果。
- 本次非法动作：B/2 COMPLETED/B-result → B/2 COMPLETED/A-result。问题是未经当前所有权授权的结果覆盖，不是“COMPLETED 不能再次出现”这一泛化规则。

## F1：旧 worker 完成 SQL 缺少所有权/代次条件

- 真实性：**已确认的合成模型内缺陷**；生产适用性与发生次数未验证。
- 不变量：I1、I2、I3。
- 可达前提：采用 guarded=false；A 暂停；B 接管并完成；A 随后恢复。合同明确允许这一时序，不依赖猜测的隐藏路径。
- 当前行为证据：scenarios.py:17–22 的无条件按 id 写；observed.json:15–32 的 B-result→A-result、affected=1。提供的轨迹与源码吻合。
- 根因：完成落库时没有以 owner/generation 做同一次原子授权校验。单纯记录 owner/generation 并不拦截旧执行者。
- 业务后果：业务读到过期输出；同时状态和归属看似正确，基于 status/owner 的巡检可能无法识别。这一可读错误结果由合同支持；金额损失、权限泄露、重复外部调用等未获证据，不能断言。
- 影响：对受影响任务是结果完整性破坏，影响高；波及量与实际严重程度未知。
- 可能性：在给定时序且无条件分支下，覆盖是确定行为；生产中出现暂停和接管的概率未知，不能声称高频。
- 建议优先级：优先修复完成写入的授权条件，再补恢复与监测。项目未提供严重度标尺，不套用通用 P0/P1。
- 是否需要代码：需要在实际未保护完成入口修复；本轮只读未改。其他公共接口、DTO、数据库结构及新框架不是本结论的必要改动。
- 同根因合并：覆盖、元数据/结果错配、终态看似正常均归入 F1，不拆成三个缺陷。

### 反证复核和排除

1. guarded=true 在 :19–21 加 owner、generation 和 PROCESSING 条件，从源码推导 A/1 无法匹配 B/2，预期影响 0 行。该分支是有意义的最小修复参考。但 observed.json 明确为 false，不能用分支存在否定 F1，也不能说本轮已测通过 true 分支。
2. B 自身完成 SQL 具备 owner/generation 条件（:15），这只保护 B 的那次更新，不保护随后 A 的另一条 SQL。
3. 未见更外层栅栏不是单纯缺失证据：合同明确“全部拦截路径、无其他隐含栅栏”，因此 F1 不以猜测实际部署漏防护为前提。
4. `lease_free()` 使用事务内 PROCESSING 条件完成与 effect 主键（:77–93）。不能因 lease=NULL 就报缺陷；此独立示例也不是 lease(False) 的防护。其真正并发及崩溃表现未执行。

## 治理包、修复顺序与验收矩阵（均待授权执行）

治理包 G1 对应 F1：统一所有实际完成写入的所有权条件，并用影响行数判定成功；affected=0 应归为旧 owner/状态冲突或幂等结果，不能再次宣称写入成功。最小方向是 guarded 分支；不能只在读取后做内存判断，也不能把租期加长作为正确性修复。若实际存在不可回滚外部副作用，需要在该副作用边界单独验证 fence/幂等，本例不证明存在此类副作用。
